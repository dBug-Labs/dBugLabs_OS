# 08 · Security

What we are protecting, from whom, and how. Every control here has a task ID
(SEC-xx) owned by [Cybersecurity](../teams/cybersecurity.md), with the code
changes done by [Web backend](../teams/web-backend.md).

---

## What we are protecting

| Asset | Why it matters |
|---|---|
| The ability to issue certificates | Anyone who can issue can create a "genuine" dBug Labs certificate for anyone. This is the crown jewel. |
| The `certificates` collection | It is the proof. Altered or deleted records make real certificates fail verification. |
| Recipients' email addresses | Personal data of students. Must not leak publicly. |
| The club's sending reputation | Spam or phishing sent through our SMTP account gets the account blocked or flagged. |
| Secrets: `ADMIN_PASSWORD`, `SESSION_SECRET`, `SMTP_PASS`, `MONGODB_URI`, `CRON_SECRET` | Each one unlocks one of the above |

## Who might attack

| Actor | Realistic goal |
|---|---|
| A participant | Get a certificate they did not earn, or edit theirs (new name, better title) |
| A curious student | Find the admin page, guess the password, list other people's certificates |
| An outsider with a fake certificate | Make a forged certificate pass verification |
| A former committee member | Keep access after leaving |
| Automated scanners | Hit every URL on the domain looking for weak spots |

## Threats and controls

| # | Threat | Control | Task |
|---|---|---|---|
| T1 | Guessing the admin password | ≥16 random characters; 5 attempts per 15 min per IP; constant-time compare | SEC-01, SEC-02 |
| T2 | Forging or extending a session cookie | HMAC-signed expiry; key includes the password; `HttpOnly` | SEC-02 |
| T3 | Cross-site request forgery (a malicious page makes the admin's browser call our API) | `SameSite=Lax`; every write requires `Content-Type: application/json` (415 otherwise) | SEC-02 |
| T4 | Ex-member keeps access | Rotate `ADMIN_PASSWORD` at every committee change; rotation logs everyone out | SEC-01 |
| T5 | Forged certificate | The QR and ID only verify if the record exists; the verify page reads only our database | by design |
| T6 | Editing a real certificate's image | The verify page shows the **recorded** name and title; a mismatch is visible | by design + PR copy |
| T7 | Listing everyone's certificates by walking sequential IDs | Decision SEC-03; rate limit SEC-04 | SEC-03, SEC-04 |
| T8 | Harvesting email addresses from the verify page | Email masked to `ab•••@domain` | SEC-05 |
| T9 | HTML injection into club emails through CSV values | Every value escaped; Drive link must be http(s) | SEC-06 |
| T10 | Spreadsheet formula injection through the exported failures CSV | Cells starting with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'` | SEC-07 |
| T11 | Script injection on the verify page | React escapes text; no `dangerouslySetInnerHTML` anywhere | SEC-06 |
| T12 | Clickjacking the admin pages | `X-Frame-Options: DENY`, `frame-ancestors 'none'` | SEC-08 |
| T13 | Secrets leaking through the repo, client bundle or logs | `.env*` ignored; no `NEXT_PUBLIC_` secrets; errors logged server-side only | SEC-09 |
| T14 | Anyone calling the drain endpoint to spam the outbox | It only sends mail already queued; requires `CRON_SECRET` | SEC-10 |
| T15 | Database credentials reused from another app | Separate Atlas database user for this app, access only to its own database | SEC-09 |
| T16 | Search engines indexing admin or verify pages | `robots: noindex, nofollow` on every page | SEC-08 |

## Controls in detail

### SEC-01: password policy

- At least 16 characters, generated by a password manager, never a word or the club name.
- Stored in Vercel environment variables (Production and Preview have **different** passwords) and in the club's password manager. Never in WhatsApp, email, the repo, or this documentation.
- Rotated: at every committee handover, when anyone with access leaves, and immediately if it is ever pasted somewhere public.
- Rotation procedure: [10 Ops](10-deployment-and-ops.md#runbook-rotate-the-admin-password).

### SEC-02: login and session review

Cybersecurity reviews the Phase 1 pull request against [03 Auth](03-auth.md)
before it merges, and checks at least:

- [ ] A missing `ADMIN_PASSWORD` makes every login fail; it never allows an empty password.
- [ ] A `SESSION_SECRET` under 32 characters stops the app from signing or verifying.
- [ ] Changing one character of the cookie's expiry or signature gives 401.
- [ ] An expired cookie gives 401 even if the browser still sends it.
- [ ] Every admin API route returns 401 without the cookie (not just the pages).
- [ ] A cross-origin `fetch` with `credentials: 'include'` to a write endpoint does not carry the cookie.
- [ ] A `POST` with `Content-Type: text/plain` or a form encoding gets 415.
- [ ] `?next=//evil.com` and `?next=https://evil.com` land on `/admin/certificates`.
- [ ] The 6th wrong login within 15 minutes gets 429.

### SEC-03: credential ID enumeration

**The problem.** Sequential IDs (`DBUG-WS-26-0001`, `…-0002`, …) let anyone
with one certificate walk the whole sequence on the public verify endpoint and
list every recipient's name, event, date and masked email. SQAC has this
problem today.

**Options.**

| Option | Format | Pros | Cons |
|---|---|---|---|
| A. Keep sequential | `DBUG-WS-26-0007` | Short, readable, SQAC-compatible | Fully enumerable |
| B. Sequential + random suffix | `DBUG-WS-26-0007-K3F9` | Still readable and ordered; guessing a valid ID needs about 1 million tries per number (4 characters from a 32-letter alphabet without look-alikes) | 5 characters longer on the certificate |
| C. Random only | `DBUG-7KQ2-M9XH` | Not enumerable | Loses the per-event numbering people like; harder to read out |

**Recommendation: B.** The verify endpoint looks up the full ID, so the suffix
makes a guessed ID almost always "not found", while the certificate stays
readable. Suffix alphabet: `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no `0/O`,
`1/I/L`), generated with `crypto.randomInt`.

**Decision needed by:** start of M2. Owner: Cybersecurity lead, with Events
lead (who reads these IDs out at events). Record the decision here and in
[05 Data model](05-data-model.md#credential-id-format).

### SEC-04: verify rate limit

Public verify endpoints (`/verify/*` and `/api/certificates/verify/*`) are
limited to **60 lookups per minute per IP**, returning 429 above it. A person
scanning a QR never comes close; a script walking IDs is slowed sharply. Same
in-process limiter as login, so it is per instance (acceptable alongside
SEC-03 option B).

### SEC-05: personal data

| Data | Where it appears | Rule |
|---|---|---|
| Full email | Database, admin log, outbox | Admin only |
| Masked email | Verify page and API | `ab•••@domain` |
| Name, title, event | Verify page | Public by design: it is what a certificate says |
| Participant CSVs | Organisers' laptops | Never committed. Deleted from shared drives once the batch is issued, unless Events needs them. |
| Spooled images | `mail_outbox` | Deleted on send or after 48 h automatically |

If a participant asks to be removed: revoke the certificate (it will verify
as revoked, without the email), or have Web backend delete the record if they
want it gone entirely. Deleting means their printed QR will show "not found".

### SEC-06: output escaping

- Email HTML: every interpolated value escaped ([07](07-email-and-outbox.md#escaping)).
- Pages: values rendered as React text only. A code search for `dangerouslySetInnerHTML` must return nothing.
- Drive links: accepted only as `http:` or `https:` URLs, so `javascript:` links cannot reach a mail.

### SEC-07: CSV export safety

The failures export is opened in Excel or Google Sheets. A cell starting with
`=`, `+`, `-`, `@`, a tab or a carriage return can run as a formula. Every
exported cell is quoted (`"` doubled) **and** prefixed with `'` when it starts
with one of those characters.

### SEC-08: HTTP headers

Set for every response in `next.config.mjs`:

| Header | Value |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Content-Security-Policy` | `frame-ancestors 'none'` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `Cache-Control` (on `/api/*`) | `no-store, max-age=0` |

Plus `robots: { index: false, follow: false }` in the root metadata.

### SEC-09: secrets handling

- Only `.env.example` (with empty values) is committed. `.gitignore` ignores `.env*` except that file.
- No secret is ever prefixed `NEXT_PUBLIC_`.
- The MongoDB user for this app has `readWrite` on this app's database only, not on the recruitment database or any other.
- Production and Preview use different values for every secret.
- Secrets are never printed in logs or returned in an error. Server logs say what failed, not the values involved.
- Before M4, run a secret scan over the git history (e.g. `gitleaks detect`).

### SEC-10: drain endpoint

- Requires `CRON_SECRET` (≥32 random characters). Missing on the server → 503, never "open".
- It can only send rows already in the outbox; it cannot create mail. The worst an attacker with the secret can do is make due mail go out sooner.

## Pre-launch security review (SEC-11)

Before M4 closes, Cybersecurity runs through this list on the production
deployment and records the result in the M4 pull request.

- [ ] SEC-02 checklist passes on production.
- [ ] SEC-03 decision implemented; a guessed ID returns "not found".
- [ ] SEC-04: 61 verify requests in a minute from one IP get a 429.
- [ ] A CSV containing `<script>`, `<a href>` and `=HYPERLINK(...)` values produces escaped emails, an escaped verify page and a safe export.
- [ ] Headers from SEC-08 present (check with `curl -I`).
- [ ] `gitleaks` finds nothing in the repo history.
- [ ] Vercel environment variables reviewed: no secret is shared between Production and Preview.
- [ ] The Atlas database user can only reach the app's own database.
- [ ] Deployment Protection is on for Preview deployments.
